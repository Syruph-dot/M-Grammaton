# M-Grammaton 持久化设计

## 一、总览

```
data/
├── {node_name}.md          # 每个节点一个文件（扁平，无子目录）
├── {node_name}.md          #
├── ...                     #
├── meta/                   # 拓扑关系与全局状态
│   ├── edges.json          # 所有边的权重
│   ├── tags.json           # 标签定义与关联
│   ├── quest_board.json    # 任务板状态
│   ├── operators.json      # Operator 锚点与提交记录
│   └── graph.json          # 全局元信息
```

**核心原则**：
- **节点即文件**：每个 `.md` 文件是一个自描述的节点。即使 `meta/` 丢失，节点内容也不丢。
- **meta/ 管拓扑**：边、标签关系、任务队列等跨节点结构统一放 `meta/`。
- **名字即主键**：节点名是唯一标识，贯穿 `.md` 文件名和 `meta/` 中的引用。

## 二、节点文件格式

### 2.1 通用 Node

`data/{name}.md`：

```markdown
---
name: "dopp63"
kind: "document"
title: "蓬莱人形C63版本译文"
tags: ["touhou", "蓬莱人形","东方Project"]
t_read: 1715200000.0
t_write: 1715200000.0
t_lp: 1715200120.5
parent: null
metadata:
  author: "ZUN"
  source: "东方Project"
stk:
  - [true, "quest_0"]     # [reaction, target_node_name]
  - [false, "node_B"]
---

They say that even the servants to the Emperor Qin Shi Huang...
（content 全文）
```

**字段映射**：

| Node 属性 | 序列化位置 | 格式 | 说明 |
|-----------|-----------|------|------|
| `name` | frontmatter | `str` | 主键，必须与文件名一致 |
| `kind` | frontmatter | `str` | `document` / `directory` / `quest` / `answer` 等 |
| `title` | frontmatter | `str` | 显示标题，默认等于 name |
| `content` | **body** | raw text | 正文内容放 body，支持多行 markdown |
| `tags` | frontmatter | `list[str]` | 标签名集合 |
| `parent` | frontmatter | `str \| null` | 父节点名，`null` 表示根节点 |
| `t_read` | frontmatter | `float` | Unix 时间戳 |
| `t_write` | frontmatter | `float` | Unix 时间戳 |
| `t_lp` | frontmatter | `float` | 最后活跃时间（EMA） |
| `metadata` | frontmatter | `dict` | 任意键值，自由扩展 |
| `stk` | frontmatter | `list[[bool, str]]` | 响应栈：`[reaction, target_name]` |

不持久化的字段：
- `children`：由 `parent` 反向推导重建
- `outlinks` / `inlinks`：由 `meta/edges.json` 重建
- `_mg`：运行时引用
- `__weakref__`：CPython 内部槽

### 2.2 QuestNode

继承 Node，增加字段：

```markdown
---
name: "quest_3"
kind: "quest"
quester_id: "Alice"
answers:
  - "Bob: 我认为..."
  - "Carol: 从另一个角度看..."
scores:
  - [0.85, 0.60]        # [匹配度, 新颖度]
  - null                 # 未评分
from_ids:
  - "Bob"
  - "Carol"
---
# 如何定义 consciousness？

这道题探讨...
```

| QuestNode 属性 | 序列化位置 | 格式 |
|---------------|-----------|------|
| `quester_id` | frontmatter | `str` |
| `answers` | frontmatter | `list[str]` |
| `scores` | frontmatter | `list[[float, float] \| null]` |
| `from_ids` | frontmatter | `list[str]` |

### 2.3 子类判别

加载时根据 `kind` 字段决定实例化哪个类：
| kind | 类 |
|------|-----|
| `document` / `directory` / `folder` / `collection` | `Node` |
| `quest` | `QuestNode` |

新增类型只需注册 kind → class 映射。

## 三、meta/ 文件格式

### 3.1 edges.json

```json
{
  "edges": [
    {"s": "dopp63", "t": "quest_0", "v": 0.85},
    {"s": "op_Alice", "t": "op_Bob", "v": 0.42},
    {"s": "op_Alice", "t": "quest_0", "v": 0.70}
  ]
}
```

- `s`：源节点名
- `t`：目标节点名
- `v`：权重 ∈ [0, 1]
- 仅存储有向边，无向边存两条
- 加载时按 `s` 分组重建 `outlinks`，按 `t` 分组重建 `inlinks`

**为什么不存 stk 在 edges.json？** 因为 stk 是源节点本地的响应历史，跟随节点文件更自然。

### 3.2 tags.json

```json
{
  "tags": [
    {
      "name": "epistemology",
      "outlinks": ["node_1", "node_3"],
      "conc_tags": {"ontology": 3, "knowledge": 2},
      "aliases": ["认识论", "知识论"]
    },
    {
      "name": "ontology",
      "outlinks": ["node_2"],
      "conc_tags": {},
      "aliases": ["本体论"]
    }
  ]
}
```

| Tag 属性 | JSON 字段 | 说明 |
|----------|-----------|------|
| `name` | `"name"` | 主键 |
| `outlinks` | `"outlinks"` | 关联的节点名列表 |
| `conc_tags` | `"conc_tags"` | 概念标签 → 关联强度 |
| `aliases` | `"aliases"` | 同义标签名列表 |

加载后 `conc_tags` 和 `aliases` 中的 Tag 引用通过 name 反查恢复。

### 3.3 quest_board.json

```json
{
  "active": ["quest_3", "quest_5"],
  "completed": ["quest_0", "quest_1", "quest_2", "quest_4"]
}
```

QuestNode 的内容在各自的 `.md` 文件中，这里只记录队列状态。

### 3.4 operators.json

```json
{
  "operators": {
    "Alice": {
      "current_node": "op_Alice",
      "submitted_quests": ["quest_3", "quest_7"]
    },
    "Bob": {
      "current_node": "op_Bob",
      "submitted_quests": ["quest_5"]
    }
  }
}
```

| Operator 属性 | JSON 字段 | 说明 |
|--------------|-----------|------|
| `id` | (作为 key) | Operator 标识 |
| `current` | `"current_node"` | 当前注意力节点名 |
| `submitted_quests` | `"submitted_quests"` | 该 Operator 发出的所有 quest |

### 3.5 graph.json

```json
{
  "version": "0.1",
  "last_save": 1715200000.0,
  "node_count": 42,
  "edge_count": 156,
  "tag_count": 8,
  "operator_count": 4
}
```

轻量级元信息，用于快速校验和统计。

## 四、文件名规则

### 4.1 合法字符

节点名作为文件名时，必须满足跨平台约束：

- 禁止字符：`< > : " / \ | ? *`
- 禁止以 `.` 或空格结尾（Windows）
- 禁止 Windows 保留名：`CON, PRN, AUX, NUL, COM1..9, LPT1..9`（不区分大小写）
- 不允许空名

### 4.2 校验策略

**方案 A（推荐）**：在 `Node.__init__` 中校验，非法字符直接拒绝。文件名 = `{name}.md`。

**方案 B**：在持久化层做映射（sanitize → 维护 `_name_map.json`）。增加复杂度，且文件名不直观。

采用方案 A。项目已有命名惯例（`dopp62`, `quest_3`, `op_Alice`），天然合法。

### 4.3 唯一性

节点名全局唯一。`mg.add_node` 和文件写入时均需校验。同名节点 = 同一节点。

## 五、读写流程

### 5.1 全量保存

```
save_graph(mg, board, operators, tags):
  1. data/.tmp/ 创建临时目录
  2. 对每个 node in mg.V:
     - 序列化为带 frontmatter 的 .md → data/.tmp/{name}.md
  3. 收集所有 edge → data/.tmp/meta/edges.json
  4. 收集所有 tag → data/.tmp/meta/tags.json
  5. 收集 board 状态 → data/.tmp/meta/quest_board.json
  6. 收集 operator 状态 → data/.tmp/meta/operators.json
  7. 写入 graph.json
  8. 原子替换：删除旧的 data/.tmp/ → 将 data/.tmp/ 重命名为 data/
     (或者逐个文件 rename 覆盖，保证部分失败可恢复)
```

实际上，Windows 不支持原子目录替换。改为：

```
save_graph:
  1. 对每个 node，生成 .md 内容
  2. 先写 .tmp 后缀（如 data/{name}.md.tmp），完成后再 rename 覆盖
  3. meta/ 文件同理：先写 .tmp 再 rename
  4. 最后写 graph.json（作为"保存完成"信号）
```

### 5.2 全量加载

```
load_graph(data_dir) → (mg, QuestBoard, dict[operator], dict[tag]):
  1. 检查 data/meta/graph.json 存在 → 验证版本
  2. 遍历 data/*.md：
     - 解析 frontmatter + body
     - 根据 kind 实例化 Node / QuestNode
     - 暂存 parent 名（延后装配）
  3. 加载 meta/edges.json → 重建所有 Edge，装配 outlinks/inlinks
  4. 加载 meta/tags.json → 重建 Tag，反查节点引用
  5. 加载 meta/quest_board.json → 重建 QuestBoard
  6. 加载 meta/operators.json → 重建 Operator 状态
  7. 装配 parent/children 树
  8. 将所有 node 加入 mg.V
```

### 5.3 单节点保存（增量更新）

```
save_node(node):
  - 序列化该节点 → data/{name}.md.tmp → rename data/{name}.md
  - 同时更新 meta/edges.json（该节点的出边/入边变更）
  - 如果该节点是 QuestNode，更新 meta/quest_board.json
```

单节点保存用于高频更新场景（如 stk 变化、content 修改）。

## 六、stk 压缩策略

`stk` 可能随时间线性增长。在写入前做一次压缩：

```
compress_stk(stk):
  - 相邻同 sign 的条目仅保留最近 N 个（默认 20）
  - 全部同 sign → 仅保留最近 N 个
  - 过长（>100）→ 截断至尾部 50 个
```

压缩后的 stk 写入 `.md` 的 frontmatter 不会过于臃肿。

## 七、Frontmatter 解析细节

### 7.1 YAML 序列化规则

- `tags`: 用 YAML flow style `[a, b, c]`
- `stk`: 用 YAML flow style `[[true, "target"], [false, "target2"]]`
- `metadata`: 展开为 YAML map
- `scores`: `[[0.85, 0.60], null]`
- `parent`: `null` 或 `"parent_name"`

### 7.2 Body 处理

- `content` 直接作为 markdown body
- 如果 content 以 `---` 开头（与 frontmatter 冲突），在前面插入一个空行
- multiline content 保持原样

### 7.3 Python 库选型

- `python-frontmatter`：轻量，专门处理 markdown + YAML frontmatter
- 或手动用 `yaml.safe_load` + 字符串分割（无额外依赖）

## 八、实现规划

### Phase 1：核心序列化（最小可用）

- [ ] `serialize_node(node) → str`：Node → .md 字符串
- [ ] `deserialize_node(md_text) → Node | QuestNode`：.md 字符串 → Node
- [ ] `save_graph(mg, path)`：全量保存
- [ ] `load_graph(path) → mg`：全量加载

### Phase 2：meta 层

- [ ] `save_edges(mg, meta_path)`：边拓扑序列化
- [ ] `load_edges(meta_path, node_map) → edges`：边拓扑反序列化
- [ ] QuestBoard / Operator / Tag 的序列化/反序列化

### Phase 3：增量与健壮性

- [ ] `save_node(node)`：单节点增量保存
- [ ] `compress_stk(stk)`：stk 压缩
- [ ] 文件名校验
- [ ] 损坏恢复（meta 缺失时从节点文件重建拓扑）
